# Recorded local work

Use the project Python environment and the entry documented in [README](../README.md).
Only sealed present_files are formal computational results. A sealed development
tree is not release evidence and does not establish an experimental outcome.

## Workflow

1. Run describe. Read the selected ACTION declaration and its input contract.
   CHECK capabilities are invoked by assurance; they do not belong in a plan.
2. Create an empty run. Submit goal declare with a UTF-8 request file containing
   original_request, targets and computable constraints. Each source uses from;
   the engine copies it and records its actual hash. Read the stored goal to
   obtain relative input paths. Original source paths are not retained.
   Omit constraint origin; the program derives it from source_quote. Read the
   selected constraint CHECK's parameter schema before declaring the goal.
3. Submit a pipeline with advance why statements and target bindings. Admission
   performs no business calculation. Correct every reported input error first.
4. Execute. On failure, retain the record and use pipeline revise to add a new
   step and supersede the failed step. Goal changes use goal amend with a reason.
5. Judge, inspect every FAIL or UNKNOWN, then seal. Earlier self-reports and
   host expectations cannot satisfy final obligations.
6. Verify the sealed directory and present only the receipt's present_files.
   Use record render for the run card and technical details. Describe unverified
   items as unverified; retain failed and superseded steps.

External Kits execute local code with user permissions; no sandbox is provided.
Use only authorized local files. The software makes no network requests and
installs nothing. Human review signing is unavailable in this development stage.
